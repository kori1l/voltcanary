================================================================================
1. PRODUCT OVERVIEW
================================================================================

VoltCanary is a predictive IoT analytics platform for connected appliances and
small physical assets.

The platform collects telemetry from smart plugs and sensors, stores time-series
data on the server side, builds baselines of normal device behavior, detects
anomalies, calculates degradation/failure risk, creates explainable
recommendations, and shows charts, forecasts, alerts, and maintenance insights
to the user through a web account.

Core product idea:

Smart plugs and sensors produce raw measurements.
VoltCanary turns these raw measurements into engineering conclusions:

- Is device behavior changing?
- Is consumption growing?
- Are there anomalies?
- Is maintenance recommended?
- How confident is the system?
- What factors influenced the risk score?

The first stage focuses on smart plug data:

- active power
- voltage
- current
- energy
- relay state
- signal quality / RSSI
- online/offline status

Later stages extend the platform with:

- temperature
- humidity
- pressure
- vibration
- door/open-state sensors
- leak sensors
- CO2 / air quality
- external weather
- device-specific API metrics

The platform must not promise exact failure diagnosis without enough data.
The system should use careful wording: signs, deviations, probabilities,
confidence levels, and recommended checks.

3. HIGH-LEVEL SYSTEM CONTEXT
================================================================================

External actors:

1. End User
   Uses web cabinet to view devices, charts, risk score, anomalies,
   recommendations, alerts, and maintenance history.

2. Administrator / Analyst
   Reviews models, quality metrics, datasets, training runs, and model versions.

   Sends telemetry through REST, MQTT, CSV import, webhook, or vendor adapter.

        ->

        ->
Web Dashboard + Notifications

================================================================================
4. ARCHITECTURAL STYLE
================================================================================

Target architecture:
Microservice-based, event-driven, production-like architecture.

Implementation strategy:
Use a private monorepo with separate deployable services.

Important principle:
Design the target architecture as a real production system, but implement the
MVP in small vertical slices.

Recommended first MVP services:

- api-gateway
- identity-service
- device-service
- ingestion-service
- telemetry-service
- analytics-service
- alert-service
- ml-service
- frontend

Target future services:

- recommendation-service
- notification-service
- report-service
- mqtt-ingestion-service
- csv-import-service
- weather-adapter-service
- vendor-adapter-services
- model-registry-service, if ML service becomes too large

Architecture principles:

1. Services own their data.
2. Internal communication uses REST for queries/commands and events for async flows.
3. Telemetry ingestion is decoupled from telemetry processing.
4. Device telemetry is stored in a time-series database.
5. Analytics results must be explainable.
6. ML service is separate from Java backend services.
7. The system must support idempotency and duplicate detection.
8. Data quality must be tracked explicitly.
9. Kubernetes is the production-like deployment target.
10. Docker Compose is used for local development.
11. The project must have documentation, ADRs, API contracts, and event contracts.

7.4 Ingestion Service

Responsibility:
Accept telemetry from REST/MQTT/CSV/API, validate it, and publish raw telemetry
events to the broker.

Port:
8083

Input methods:
- REST ingestion API: MVP
- MQTT ingestion: MVP/v1
- CSV import: MVP/v1
- Webhook/WebSocket: later
- Home Assistant: later
- Vendor adapters: later

API:
POST /ingestion/readings
POST /ingestion/readings/batch

Minimum telemetry format:
{
  "deviceId": "device-123",
  "sourceId": "plug-001",
  "timestamp": "2026-05-12T12:30:00Z",
  "metrics": {
    "activePowerW": 840.2,
    "voltageV": 230.1,
    "currentA": 3.65,
    "energyWh": 12450.7,
    "relayState": "ON",
    "rssi": -61
  }
}

Responsibilities:
- accept REST telemetry
- validate required fields
- validate timestamp
- validate metric names and types
- verify device/source exists
- apply idempotency
- publish TelemetryReceived event to telemetry.raw.v1
- handle batch ingestion
- publish invalid events to DLQ or reject with validation error
- support CSV/MQTT later

Kafka topic:
telemetry.raw.v1

Kafka key:
deviceId

Reason:
Events from one device should be processed in order within the same partition.

Idempotency key:
deviceId + sourceId + timestamp + metricName

Later:
Use Redis/PostgreSQL to store processed request ids or payload hashes.

- TelemetryQualityFlag
- TelemetryAggregate
- LatestReading

API:
GET /telemetry/devices/{deviceId}/readings
GET /telemetry/devices/{deviceId}/latest
GET /telemetry/devices/{deviceId}/quality
GET /telemetry/devices/{deviceId}/aggregates

Responsibilities:
- consume telemetry.raw.v1
- normalize metric values and units
- save time-series readings
- detect duplicate readings
- detect out-of-order readings
- detect invalid values
- detect missing data later
- add quality flags
- update latest readings in Redis
- create aggregates for chart performance
- publish telemetry.validated.v1

Quality flags:
- OK
- DUPLICATE
- OUT_OF_ORDER
- MISSING_FIELD
- INVALID_VALUE
- LATE_ARRIVAL
- UNKNOWN_METRIC

TimescaleDB tables:
- telemetry_readings
- telemetry_quality_flags
- telemetry_aggregate_1m
- telemetry_aggregate_5m
- telemetry_aggregate_1h
- telemetry_aggregate_1d

Downsampling strategy:
- less than 6 hours: raw or 1m
- less than 7 days: 5m
- less than 90 days: 1h
- more than 90 days: 1d

7.6 Analytics Service

Responsibility:
Calculate baselines, features, trends, anomalies, risk score, explanations,
recommendations, and call ML service.

Port:
8085

Owns database:
analytics_db

Consumes:
telemetry.validated.v1

Publishes:
baseline.updated.v1
features.calculated.v1
anomaly.detected.v1
risk-score.changed.v1
recommendation.created.v1
model-inference.completed.v1

Main entities:
- DeviceBaseline
- FeatureSet
- Anomaly
- RiskScore
- PredictionResult
- Recommendation
- AnalyticsJob

API:
GET  /analytics/devices/{deviceId}/baseline
GET  /analytics/devices/{deviceId}/features
GET  /analytics/devices/{deviceId}/cycles
GET  /analytics/devices/{deviceId}/anomalies
GET  /analytics/devices/{deviceId}/risk
GET  /analytics/devices/{deviceId}/forecast
GET  /analytics/devices/{deviceId}/recommendations
POST /analytics/devices/{deviceId}/recalculate

Responsibilities:
- build baseline for each device/metric
- baseline by time of day
- baseline by day of week later
- calculate mean/median/percentiles
- extract work cycles
- calculate energy per cycle
- calculate cycle duration
- calculate idle time
- calculate start/stop frequency
- calculate rolling mean/std
- calculate slope
- detect anomalies
- calculate risk score 0-100
- classify risk level
- generate explanations
- generate recommendations
- call ML service for inference
- store modelVersion for reproducibility

MVP anomaly types:
- POWER_SPIKE
- LONG_CYCLE
- CONSUMPTION_GROWTH

Later anomaly types:
- TOO_FREQUENT_SWITCHING
- MISSING_EXPECTED_ACTIVITY
- OFFLINE
- SENSOR_CONFLICT
- CHANGE_POINT

Risk levels:
0-30: LOW
31-60: MEDIUM
61-80: HIGH
81-100: CRITICAL

Example risk score formula:
riskScore =
  anomalyScore * 0.35
+ trendScore * 0.25
+ cycleDeviationScore * 0.20
+ dataQualityRisk * 0.10
+ offlineRisk * 0.10

Explanation examples:
- Average runtime increased by 22% over the last 14 days.
- Energy per cycle is above the historical baseline.
- Power spikes were detected 4 times in the last 24 hours.
- Data quality is low because 18% of readings are missing.

Important wording rule:
Do not say: "The air conditioner definitely has a refrigerant leak."
Say: "The air conditioner behavior has changed. Work cycle duration increased
and energy consumption is higher under similar conditions. Loss of efficiency is
possible. Check filter and operating mode, and contact a technician if the
anomaly repeats."

9. INTERNAL EVENTS
================================================================================

Event naming convention:
domain.event-name.v1

Examples:
telemetry.raw.v1
telemetry.validated.v1
device.status-changed.v1
analytics.baseline-updated.v1
analytics.features-calculated.v1
analytics.anomaly-detected.v1
analytics.risk-score-changed.v1
analytics.recommendation-created.v1
ml.model-inference-completed.v1
alerts.alert-created.v1
alerts.alert-acknowledged.v1
alerts.alert-resolved.v1
maintenance.maintenance-logged.v1

Event envelope:
{
  "eventId": "uuid",
  "eventType": "TelemetryReceived",
  "eventVersion": 1,
  "occurredAt": "2026-05-12T12:30:01Z",
  "correlationId": "uuid",
  "producer": "ingestion-service",
  "payload": {}
}

TelemetryReceived:
- Purpose: Raw data received from source.
- Produced by: ingestion-service
- Consumed by: telemetry-service
- Topic: telemetry.raw.v1

TelemetryValidated:
- Purpose: Telemetry has been normalized, validated, and stored.
- Produced by: telemetry-service
- Consumed by: analytics-service
- Topic: telemetry.validated.v1

DeviceStatusChanged:
- Purpose: Device became online/offline or changed state.
- Produced by: telemetry-service or device-service
- Consumed by: analytics-service, alert-service

BaselineUpdated:
- Purpose: Device baseline has been recalculated.
- Produced by: analytics-service

FeaturesCalculated:
- Purpose: Features for model or rule-based analytics have been calculated.
- Produced by: analytics-service

ModelInferenceCompleted:
- Purpose: ML service returned forecast/anomaly/risk/confidence/explanations.
- Produced by: analytics-service or ml-service through orchestrated event

AnomalyDetected:
- Purpose: An anomaly was detected.
- Produced by: analytics-service
- Consumed by: alert-service, notification-service later

RiskScoreChanged:
- Purpose: Risk score or risk level changed.
- Produced by: analytics-service
- Consumed by: alert-service, frontend projection later

RecommendationCreated:
- Purpose: A recommendation was created.
- Produced by: analytics-service or recommendation-service later

AlertCreated:
- Purpose: An alert was created.
- Produced by: alert-service
- Consumed by: notification-service later

MaintenanceLogged:
- Purpose: User added maintenance event.
- Produced by: analytics-service/device-service later
- Consumed by: analytics-service, ml-service

25. IMPORTANT TRADE-OFFS
================================================================================

Monorepo:
Pros:
- easier for one developer
- easier local setup
- easier CI/CD
- docs near code

Cons:
- can grow large
- requires discipline around service boundaries

Microservices:
Pros:
- close to production system
- independent scaling
- strong interview value
- clear domain boundaries

Cons:
- more infrastructure
- harder local development
- requires observability and contracts

TimescaleDB:
Pros:
- PostgreSQL-compatible
- good for time-series
- easier than ClickHouse/InfluxDB for MVP
- SQL-friendly

Cons:
- may not be enough for very large scale later

Redpanda/Kafka:
Pros:
- Kafka-compatible
- simpler local setup
- good for event-driven architecture

Cons:
- adds operational complexity

Python ML service:
Pros:
- natural ML ecosystem
- easy model experimentation
- separation from Java backend

Cons:
- cross-language deployment
- service contract required

27. SHORT PROJECT DESCRIPTION FOR README
================================================================================

VoltCanary is a predictive IoT analytics platform for connected appliances and
small physical assets.

It collects telemetry from smart plugs and sensors, builds a baseline of normal
behavior, detects anomalies, trains and compares multiple analytical models,
calculates degradation risk, and provides users with charts, alerts, forecasts,
and maintenance recommendations.
