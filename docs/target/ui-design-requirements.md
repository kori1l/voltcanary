# Требования к улучшению интерфейса VoltCanary

Первичный аудит: 5 октября 2026 года. Его девять UI changes реализованы и
заархивированы 7 октября; описание ниже сохраняет исторические наблюдения.
Актуальный список оставшихся правок — в разделе
[повторного UI/UX-аудита от 7 октября](#uiux-audit-2026-10-07).

## Вывод

Приоритет редизайна — восстановить целостность операционной консоли:
устранить выход элементов за границы, унифицировать формы, сделать состояния
данных честными и упростить путь от проблемы устройства к действию оператора.
Замена цветов сама по себе этих проблем не решит.

Предлагаемое направление: светлая рабочая консоль с нейтральными поверхностями,
компактной навигацией, одним акцентом для основных действий и цветом статуса
только там, где он передаёт смысл. Жёлтую птицу и узнаваемость VoltCanary
сохранить. Конкретные цвета и макеты следует утвердить на прототипах.

## Метод и ограничения

- Просмотр выполнен в браузере по реальному frontend на `http://127.0.0.1:3000`.
  Основной размер — 1280 × 720; дополнительно проверены 390 × 844 и 768 × 1024.
- Проверены все 15 маршрутов экранов из `frontend/src/app/App.tsx`, семь вкладок
  устройства и восемь вкладок ML. Формы раскрывались через существующие кнопки.
  Отдельные состояния без необходимых записей изучены по исходному коду;
  это не равнозначно их визуальной проверке с данными.
- Стандартный `docker compose --profile app up -d` завершился ошибкой загрузки
  `minio/minio:RELEASE.2025-04-22T22-12-26Z` (`pull access denied`).
  Повторная загрузка и попытка загрузки того же тега из Quay не помогли.
- Для продолжения запущены Java-сервисы и инфраструктура без зависимости запуска
  от MinIO через временный override в системном TEMP; ML запущен с локальным
  хранилищем артефактов. Frontend запущен локальным Vite. Compose репозитория
  для аудита не изменялся. Это ограниченный режим, а не подтверждение полного
  production-подобного запуска или ML lifecycle.
- Во время последовательного запуска были доступны состояния ошибок сервисов.
  Они использованы как реальные примеры отображения отказа, а не как доказательство
  постоянной неисправности backend.
- Созданы отдельные локальные тестовые записи: учётная запись аудита, локация,
  устройство с симулятором, запись обслуживания и правило порога без каналов
  доставки. Реальные ключи провайдеров и адреса получателей не вводились.
- Не проверены полный набор сочетаний полей, отправка Email/Telegram/Webhook,
  реальное обучение и продвижение моделей, все варианты ошибок и доступность
  всех экранов для каждой роли. Такие проверки входят в приёмку редизайна.
- На завершении аудита health gateway и Java-сервисов на 8080–8088 — `UP`,
  ML на 8090 — `ok`. Тестовый симулятор остановлен, тестовое правило отключено,
  временная роль ADMIN учётной записи аудита возвращена в USER. Тестовые записи
  сохранены для повторного просмотра; стек и Vite оставлены запущенными.
- Проверки документации: `npm.cmd run openspec:validate` — 18/18 успешно;
  `npm.cmd run structure:check` — успешно с предупреждениями о размерах
  существующих модулей. Frontend-код не изменялся; typecheck/test/build в рамках
  этого аудита не запускались.

## Общие требования

Приоритеты: **P0** — действие скрыто или состояние вводит в заблуждение;
**P1** — регулярный сценарий требует лишних усилий; **P2** — визуальная доработка.
Ниже «должен» означает целевое требование, а не текущее поведение.

| ID | Приоритет | Требование | Критерий приёмки |
| --- | --- | --- | --- |
| UI-01 | P0 | Адаптивная сетка должна удерживать содержимое внутри карточек; при недостатке места переходить в одну колонку | На ширинах 360, 390, 768, 1024, 1280 и 1440 px нет глобальной горизонтальной прокрутки, наложения элементов и обрезанных кнопок. Прокрутка допустима внутри таблицы/таймлайна с видимым указанием |
| UI-02 | P0 | Разделять загрузку, ошибку, отсутствие данных, отсутствие результатов фильтра и устаревшие данные | Ошибка API не даёт нулевые KPI или утверждение «нет проблем»; остаётся время последних данных, если они были, и кнопка повтора |
| UI-03 | P0 | Отсутствие измерений и прогноза отображать нейтрально | Нет зелёного «здоров» и нулевого графика при отсутствующих samples; «нет оценки» отличается от риска 0 |
| UI-04 | P1 | Ввести общие компоненты поля, select, textarea, checkbox, переключателя, кнопок и ошибок | Одинаковые высоты, шрифт, отступы, focus, disabled, busy и error во всех формах; текстовые поля обычно 40–44 px, checkbox не растягивается сеткой |
| UI-05 | P1 | Каждое поле должно иметь постоянную подпись, обязательность и при необходимости единицу/пояснение | После ввода текста смысл поля остаётся видим; доступное имя соответствует подписи; placeholder служит примером |
| UI-06 | P1 | Общий шаблон страницы: заголовок, краткий контекст, основное действие, фильтры, содержимое | Одна визуально главная кнопка на самостоятельный блок задачи; refresh/import/export и опасные операции не конкурируют с основным действием |
| UI-07 | P1 | Сгруппировать навигацию по работе с устройствами, аналитике и администрированию | Один текущий конечный пункт; родитель может быть раскрыт, но не иметь такой же активной подсветки. Название Admin согласовано с заголовком экрана |
| UI-08 | P1 | Desktop sidebar и мобильная навигация должны сохранять доступ к рабочей области | Sidebar имеет собственную прокрутку; на телефоне компактный header с меню; переход между страницами начинает основной контент сверху |
| UI-09 | P1 | Унифицировать диалоги и выдвижные панели | Непрозрачный фон, фиксированный header/footer для длинных форм, прокрутка тела, Escape, удержание и возврат фокуса, защита несохранённого ввода |
| UI-10 | P1 | Показывать ошибки возле соответствующего поля и объяснять блокировки | Ошибочный ввод сохраняется; ошибка сервера не маскируется успехом; disabled-действие имеет видимую причину и следующий шаг |
| UI-11 | P1 | Заменить `window.prompt/confirm` для действий над alerts/ML единым диалогом | Видны объект, действие, последствия, зависимости, причина и возможность отмены; подтверждение не требует двух браузерных окон подряд |
| UI-12 | P1 | Снизить требования к знанию UUID, enum, JSON и YAML в обычных сценариях | Устройство/метрика выбирается по имени; технический ID можно скопировать; JSON/YAML остаётся в Advanced; значения enum имеют понятные подписи |
| UI-13 | P1 | Клавиатура и доступность должны работать на всём основном пути | Видимый focus, логичный Tab, названия и состояния вкладок, текстовые обозначения статусов, объявление результатов операций, отсутствие зависимости только от цвета |
| UI-14 | P2 | Упростить палитру, тени и типографику | Нейтральные поверхности; 14–16 px для основного текста, мелкий текст только для вспомогательных данных; декоративные цвета не воспринимаются как статус |
| UI-15 | P1 | Даты и времена должны иметь явный часовой пояс и единый формат | Часовой пояс указан у обслуживания, графиков и quiet hours; локаль текста согласована. Русский язык интерфейса — отдельное продуктовое решение, а не вывод из языка этого аудита |

## Порядок реализации и приёмка

1. **Исправление основы (P0):** сетки и breakpoints, containment, состояния
   ошибки/нет данных, семантика цвета, пустые графики и KPI. Сначала Settings,
   Training, Policies, Devices mobile и Dashboard.

   keyboard/focus и feedback. Переносить формы на компоненты по разделам.
3. **Рабочие сценарии (P1):** устройства и onboarding → alerts → maintenance
   → уведомления → ML → admin/AI. Сохранять действующие API-контракты и правила
   неопределённости ML; новые backend-возможности оформлять отдельным OpenSpec.
4. **Полировка (P2):** типографика, палитра, плотность, иконки, состояния наведения.

### Порядок работ и приёмка

1. **Достоверность:** R01–R05, R10, R14–R16. Проверять отказы и частичный успех
   с заранее подготовленными объектами; отсутствие ответа не означает отсутствие
   инцидента/модели/попытки доставки.
2. **Основные задачи оператора:** R06–R08, R12–R13, R17–R18, R28. Пройти цепочку
   «добавить → увидеть сигнал → открыть инцидент → посмотреть интервал →
   запланировать обслуживание → записать результат» и возврат после входа.
3. **ML/телеметрия:** R02, R19–R20. Пройти одну согласованную цепочку модели,
   явно показывая scope, family, horizon и исходные доказательства.
4. **Доступность и скорость:** R09, R11, R21–R24. Проверить 360/390/768/1280/1440,
   реальное увеличение текста 200%, клавиатуру, screen reader, длинные значения,

   общий документ не является сертификатом соответствия.
5. **Полировка:** R25–R27 после фиксации поведения, без замены бренда VoltCanary.

Для продуктовых решений провести хотя бы 5–7 модерируемых сессий с
представителями операторов и инженеров/ML-пользователей. Отдельно измерять
успех задачи, время, ошибочные трактовки stale/unknown и число возвратов к
поиску нужного раздела. Размер выборки — практический старт, а не статистическая
гарантия. Зафиксировать baseline перед изменениями; не заявлять проценты
улучшения до повторных измерений. Минимальные задачи: первое подключение,
поиск устройства за первым лимитом, расследование инцидента, обслуживание,
