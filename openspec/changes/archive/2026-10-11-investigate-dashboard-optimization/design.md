# План исследования

## Границы и источники

Начать со статического разбора цепочки, затем подтвердить выводы трассами.
Начальные точки: `frontend/src/pages/PersonalDashboardsPage.tsx`,
`frontend/src/features/dashboards/components/DashboardViewer.tsx`, frontend query
hooks, `DashboardQueryController`, `QueryReadScheduler`, `HttpDashboardEvidenceReads`
и `DashboardBusinessReads`. Это точки входа, не заранее найденные bottlenecks.
Временная диагностическая инструментализация допустима, если не меняет поведение,
не пишет секреты и явно описана. Постоянные изменения требуют отдельного change.

## Воспроизводимая матрица

- Реальные demo monitoring/analyst/service/energy dashboards; видимые экраны,
  скрытые экраны, повторяющиеся и разные источники/параметры виджетов.
- Холодное открытие, тёплое повторное открытие, refresh, смена экрана/фильтра/периода,
  переход назад, editor preview, background tab и возвращение в неё.
- Контролируемые наборы 1/6/12/24 виджета и 1/10/50/250/500 устройств в пределах
  действующих контрактов; точные сценарии с меньшими лимитами соблюдают свои лимиты.
  Большие fixtures изолированы от пользовательского demo; реальность и синтетика отмечены.
- Медленный источник, ошибка одного источника, быстрые последовательные смены
  контекста, отмена запроса, истечение сессии и отзыв доступа.
- Desktop и меньший viewport для стоимости графиков; production build отдельно
  от dev/StrictMode, где повтор эффекта не доказывает production N+1.

Для каждого применимого сценария записать commit/состояние рабочего дерева,
окружение и ресурсы, конфигурацию, объём данных, метод прогрева, несколько повторов,
sample count и разброс. p50/p95 допустимы только с указанной выборкой; короткий
smoke не считается доказательством ёмкости или SLO. Невыполненные сценарии обозначить.

## Измерения и N+1

Сопоставить browser request → dashboard batch → downstream read → SQL.
Считать обращения отдельно по слоям и семействам запросов, уникальным ключам,
виджетам/устройствам/экранам, включая авторизацию и справочники. Зафиксировать
ожидаемый bounded fanout и сравнить рост при изменении N: увеличение числа
виджетов само по себе не доказывает N+1. Отдельно отметить неизбежные уникальные
чтения, повторяемые lookup и одинаковые запросы, которые можно объединить.

Измерить critical path, waterfalls, TTFB, время определения раскладки, первый
полезный виджет, все видимые виджеты, объём wire/decoded JSON, число строк/точек
полученных и реально использованных, parse/transform/render time, CPU/memory,
ошибки/таймауты и очереди. HAR/логи очищаются от токенов, cookies и персональных данных.

## Стандартный чеклист

Каждый пункт получает статус confirmed issue / no issue observed / not applicable /
unverified с основанием; рекомендации ниже являются кандидатами, не готовыми решениями.

| Область | Что проверить и сравнить |
| --- | --- |
| HTTP и композиция | N+1, одинаковые запросы, waterfall, независимый параллелизм, batch/shared reads, повторные справочники и проверки доступа, connection reuse, лимит fanout и очередь |
| Объём данных | Неиспользуемые поля и серии, дубли метаданных, слишком широкие scope/time windows, полные списки вместо paging, server-side aggregates/projections, top-N, число точек под ширину графика, downsampling с сохранением пиков/единиц |
| Cache | Request coalescing/deduplication, ключи scope/revision/context/auth, TTL/invalidation, stale-while-revalidate, ETag/conditional reads, Browser Cache-Control, hit/miss и eviction; безопасность при отзыве доступа |
| Жизненный цикл | Повтор эффектов/подписки, polling offscreen/hidden tabs, backoff/jitter, refresh overlap, cancellation, late-response races, debounce, retry storms, timeout budget, лишние reconnect/refetch |
| SQL и storage | Число SQL на batch, ORM lazy N+1, EXPLAIN (ANALYZE, BUFFERS) безопасных репрезентативных read-only запросов, индексы tenant/device/time, сортировки, scans, cardinality/statistics, rows read vs returned, pagination, pool wait/locks |
| Backend вычисления | Повтор reducers/преобразований/сериализации, allocations и memory, concurrency saturation, критическая последовательность, серверные агрегаты и повторная работа на один контекст |
| JS доставка | Размер initial route/chunks, code splitting, lazy chart dependencies, дубли библиотек, cache headers, resource waterfall; prefetch только с измеренной пользой и учётом расхода данных |
| React и графики | Render/commit count и duration, нестабильные props/keys и remounts, повтор derived transforms, SVG/DOM point count, layout thrashing/resize loops, animation, tooltip work; memoization/virtualization/worker только при подтверждённой цене |
| UX загрузки | Общий Loading vs сохранённая раскладка/виджеты, progressive panel loading, refresh indicator, layout shift, сохранение взаимодействий, partial/stale/error/no-access и retry без очистки успешных панелей |

Нельзя сокращать запросы ценой пропуска авторизации, урезанных знаменателей,
скрытой потери пиков, фиктивных нулей или изменения аналитических исключений.
EXPLAIN и контролируемые нагрузки не должны изменять продуктовые данные;
полномасштабный load/soak и capacity claims выходят за пределы этого исследования.

## Уже отрисованный дашборд во время загрузки

Сравнить минимум три варианта: сохранение текущего authorized canvas при refresh;
кеш определения/раскладки и результатов при повторном открытии; каркас известной
раскладки с независимой загрузкой панелей при отсутствии результатов. Если даже
определение ещё неизвестно, допустим нейтральный каркас, а не выдуманные виджеты.

Описать политику для first load, same-context refresh, новой ревизии/фильтра,
смены дашборда/аккаунта и отказа доступа. Разделить кеш раскладки и evidence,
ограничить размер/срок хранения, выбрать memory/session/persistent storage с
обоснованием. Старые значения при обновлении явно показывают время/состояние;
ответы другого контекста не становятся текущими. При смене аккаунта/отзыве
доступа значения и имена очищаются. Определить, как подтвердить доступ перед
повторным показом кеша, обработать stale grant и не блокировать успешные панели
из-за одной медленной зависимости. Prefetch не запускает inference/мутации.

## Выходной отчёт и решения

Отчёт — единственный источник результатов; raw artifacts остаются локальными.
Приложить метод воспроизведения, baseline-таблицу, заполненный чеклист, цепочку
и evidence-ссылки с очищенными выдержками, negative findings и ограничения.

Для каждой оптимизации: проблема и доказательство; затронутые endpoints/files;
приоритет P0/P1/P2 и confidence; ожидаемый эффект и способ его измерить;
рекомендуемый алгоритм/контракт/cache key/invalidation; альтернативы и причины
выбора; риски/совместимость; effort/dependencies; acceptance и regression checks;
рекомендуемый последующий OpenSpec scope. Количественную выгоду без прототипа
отмечать как гипотезу. Отдельно перечислить ненужные/преждевременные оптимизации.

Итог должен позволять выбрать порядок внедрения без нового общего аудита.
Доработки AGENTS.md/skills не нужны: архитектура и workflow пока не изменяются.
