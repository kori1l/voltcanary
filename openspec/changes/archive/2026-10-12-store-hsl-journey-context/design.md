# Design

Use optional `metrics.transport` object with ten whitelisted nullable fields: routeId (128), routeShortName (64), direction (1/2), destination (200), nextStopId (128), scheduleDeviationSeconds (integer +/-86400, original HSL sign), doorsOpen (boolean), accelerationMs2 (finite +/-30), scheduledStart (HH:mm), locationSource (GPS/ODO/MAN/DR/N/A). Bounded strings exclude control characters; unknown keys/types reject the optional object. Context requires an atomic GPS pair. Shared validation runs at HTTP ingress and raw broker projection. Context is skipped by numeric normalization/validated analytics events and preserved only as valid context in telemetry_readings and positions.transport_context varchar(4000).

Map payload route/desi/dir/dl/drst/acc/start/loc and topic headsign/next_stop; payload missing identifiers can use their explicit topic equivalents. Omit invalid/missing fields, do not convert missing doors to closed or stop IDs into guessed names. Retain original source timestamps and sampled 5s VP semantics; this does not subscribe to all door/stop event topics. Existing opaque source tokens, allowlist and ownership remain unchanged. Older positions have null context. Source silence does not invent a new journey state.

Add typed TransportContext to position points with compatibility constructors. Existing latest, recordings and fleet track DTOs carry it. Display selected vehicle context compactly; no expanded table columns or persistent bulky controls. Validate mapping, hostile context, storage/roundtrip/source isolation, migration, and real API evidence after deployment. Restart ingestion and telemetry before enabling the updated connector.

Nighttime verification: when no configured public VP observations are available, verify the actual migrated API and broker connection plus isolated ingestion/storage fixtures; report the absence of live context honestly. The running connector continues collection when real service resumes.
