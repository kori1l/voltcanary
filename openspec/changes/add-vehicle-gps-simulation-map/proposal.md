# Базовая GPS-эмуляция автомобиля и карта движения

Статус: предложение для реализации; функциональность ещё не реализована.

## Why

VoltCanary умеет регистрировать устройства, подключать источники и запускать
YAML-эмуляцию бытовой техники. Для демонстрации движущегося автомобиля нет
профиля GPS-датчика, согласованных географических измерений и карты.
Пользователю нужен законченный базовый сценарий без физического оборудования:
создать автомобиль, запустить его эмулируемый датчик и увидеть движение.

## What Changes

- Добавить тип устройства `VEHICLE` («Автомобиль») в существующий каталог.
  Сам автомобиль — Device; виртуальный GPS-датчик — профиль источника SIMULATOR.
- Добавить профиль симулятора `VEHICLE_GPS` и один готовый замкнутый маршрут
  `CITY_LOOP`. Он генерирует координаты, скорость и курс каждые пять секунд.
- Провести GPS-измерения по существующему ingestion/Kafka/telemetry конвейеру.
  Сохранить проверенные атомарные GPS-точки в telemetry-service.
- Добавить ограниченный API последней позиции и истории одного источника.
- Добавить вкладку «Движение» в карточку автомобиля и виджет `vehicle-map`
  версии 1 в существующие палитру, редактор и query pipeline дашборда.
- Использовать один общий компонент карты: маркер с курсом, след за период,
  скорость, время измерения, состояние свежести и переключатель следования.
- Сохранить текущие потоки создания/восстановления устройства, проверки доступа,
  конфигурации симулятора, публикации дашборда и сохранения расположения виджета.

## Базовый пользовательский сценарий

1. В существующем мастере пользователь выбирает «Автомобиль» и вводит имя.
   Марка/модель остаются существующими необязательными полями. Локация необязательна.
2. Выбирает эмуляцию. Автоматически предлагаются `VEHICLE_GPS`, `CITY_LOOP`,
   HTTP, интервал 5s, длительность 30m и скорость движения 36 km/h.
3. Мастер создаёт устройство, SIMULATOR/REST источник, credential и сохраняет
   конфигурацию через текущие этапы. Запуск — явное действие или существующий
   явно выбранный флаг «Запустить сразу»; просмотр шаблона ничего не запускает.
4. На вкладке «Движение» после поступления первого измерения появляется машина.
   Пока она едет, обновляются маркер и след последних 15 минут.
5. Пользователь добавляет «Карту автомобиля» на дашборд, выбирает машину и
   её источник, сохраняет/публикует обычным способом.
6. После остановки эмуляции карта сохраняет последнюю известную позицию;
   через 30 секунд без новых точек обозначает её как устаревшую.

## Scope / Non-Goals

Первая версия: один автомобиль и один GPS-источник на карту, один готовый
маршрут, запуск/остановка, текущая позиция и ограниченный след движения.
Отдельные автомобили могут иметь отдельные карты.

Не входят: общий fleet-map, кластеризация, геозоны/уведомления, поиск адреса,
построение маршрута по дорогам, редактор маршрута на карте, проигрывание поездки,
сущность Trip, расчёт пробега, OBD/зажигание/топливо/двигатель, ML для автомобиля,
аппаратные адаптеры, WebSocket/SSE подписка на GPS, 3D-модели, GPS-шум и аварии,
общий framework capabilities, новые микросервисы и новый Kafka topic.
Госномер/VIN и отдельная сущность Vehicle/Asset также не требуются.

## Impact

- Backend: device-service, simulator-service, ingestion-service,
  telemetry-service, dashboard-service; gateway только для маршрутизации новых
  read endpoints, если существующего `/telemetry/**` недостаточно.
- Frontend: мастер устройства, simulation helpers, вкладка движения,
  telemetry API, manifest/palette/settings/query result/renderer карты.
- Data: новая seed-миграция типа устройства; проверенная GPS-проекция с индексом
  в telemetry-service; YAML v1 расширяется только для нового профиля.
- Dependencies: MapLibre GL JS, CSS и конкретная версия в lockfile на этапе
  реализации; URL картографического стиля через frontend environment.
- Docs при реализации: `docs/current/api/{device,ingestion,telemetry,dashboard}-api.md`,
  `docs/current/simulation/{yaml-schema-v1,simulator-service,frontend-flow}.md`,
  новый verification flow и соответствующие индексы.

## Dependencies and Completion

Отдельных активных prerequisite changes на момент подготовки нет. Использовать
текущие device/source workflows, simulator lifecycle, telemetry idempotency и
typed dashboard queries, не возобновляя архивированные changes.

Порядок: контракт и тип → эмулятор → ingestion/validated storage/read API →
карточка автомобиля → виджет → сквозная проверка. Критерии и сценарии находятся
в [design.md](design.md) и delta specs; проверяемый план — [tasks.md](tasks.md).
Создание этих документов не означает выполнения implementation tasks.
